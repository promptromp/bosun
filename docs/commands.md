# Commands

| Command | What it does |
|---|---|
| `bosun preflight [--quiet]` | Check what bosun needs on this machine, for each agent in use (Claude Code, Codex, Antigravity), and say exactly what to do about anything missing. It changes nothing. `bosun init` and `bosun doctor` start with the same check. See [Setup](setup.md#requirements) |
| `bosun init [--recommended [--unattended] \| --answers <file>] [--force] [--dry-run]` / `--detect` / `--print-answers` | Set bosun up from what this Mac shows: the repos you use your agents in (Claude Code and Codex), the connectors `claude mcp list` shows, your usual hours, your logins. In a terminal it asks a few questions, among them which connectors the orchestrator may use, and shows the plan before it changes anything; otherwise it only prints the plan. `--unattended` (`get.sh --unattended` sets `BOSUN_INIT_UNATTENDED=1`, the same) sets up no repo windows or connectors on a first run, since nobody chose them. See [Setup](setup.md#install) |
| `bosun update [--dry-run] [--yes] [--json]` / `update --check [--json]` / `update --skip <version>` / `update note --window <w> --stock\|--status` / `update advance` | Update bosun to the newest release (a dated tag, `v<YYYY.MM.DD>`, a second one the same day `.2`; `BOSUN_UPDATE_CHANNEL=releases`, the default) or, with `BOSUN_UPDATE_CHANNEL=main`, to the head of the branch it tracks (`git config bosun.branch` in the versions folder's `bosun.git`, default `main`; an install from before releases keeps following it) while the agents keep working, without losing a write. An install already past the newest release says so and changes nothing. `--check` says whether there is an update and changes nothing (no version folder, no hold, no lock): it looks the newest release up with `git ls-remote` and reads its notes from the tag's message, and prints one line, or with `--json` one object (`contract`, `channel`, `installed` and `latest` as `{version, commit}` with `latest`'s `notes`, `available`, `skipped`, `ahead`, `error`); it exits 0 whatever it finds, a problem such as an origin that cannot be reached being the `error`. `--skip <version>` records a release not to be offered again (`update-skip.json` in the state folder): `--check` then reports it as `skipped`, and the next release as usual; it does not stop an update you run. The update fetches the new version into a folder of its own beside the running one, and that version shows the plan: the commits, the stores' migrations, the prompts that changed, what each window gets, the launchd jobs to reload, a running console to restart, and what stops it (something the new version needs and this Mac lacks, a store it cannot read, a link a backup cannot copy, a `kg forget` cut short). In a terminal it asks first; without one, or with `--dry-run`, it stops at the plan, and `--yes` goes ahead without asking. Then it rehearses the migrations and the stores' checks on a copy of the data, holds bosun's own background work, and pauses writes briefly: it backs the data up (`backups/` in the state folder, the last 3 kept), migrates it, switches the install link to the new version and checks each store, and on any failure puts everything back as it was. Last it reloads the launchd jobs whose plist changed, restarts the check-in loop, lifts the hold and keeps what `bosun doctor` finds. Then it brings the agents along, each as the plan says but decided again from what it is doing now: the orchestrator re-reads its prompts when only they changed; a window something it was launched with changed for restarts on the new version once idle, after listing its background work if only that runs (a restart ends it, and the list goes back in the restart's prompt); a busy window is waited for, and one waiting for you is never touched; a window bosun did not start (outside the window list, with no launch recorded: a shell or a Claude you opened in its session) is left as it is, and the plan says so. Each gets a prompt to check for anything it missed and carry on, and answers with `bosun update note --window <w> --status` (the text on stdin; `--stock` is the list before a restart); the update waits for every answer, saying which windows it waits for. Ctrl-C stops the wait and leaves them to the check-in loop, whose `bosun update advance` takes a turn at them each tick (nothing while the update itself still runs; without a check-in loop, run it by hand); the next update is blocked at its plan while they are pending. See [After an update](orchestrator.md#after-an-update-the-windows-brought-along). It ends with a short summary: the commits and how long it took, each store's migrations and version bumps, the config it changed and its new keys, what to change by hand in your own files, how many prompts changed, the jobs reloaded, the handed tasks that keep their old text, what came of each window, what fails after the switch that did not before (each `bosun doctor` FAIL with its detail that a doctor run before the hold did not show, with a count of those it did and of doctor's warnings), and where the backup is (the size of its files); it is saved as `summary.md` in the backup's folder once the update is done (by the update, the next `bosun update` or the check-in loop, whichever finishes it), and a failed update names its backup too. An update cut short is put back by the next write to a store, or by the next `bosun update`, which also finishes one whose checks had passed. `--json` prints one object on every path: the plan (`null` when none was made, as when it is up to date or refused), the update's record as it stands, and the summary (`null` unless an update ended in that run). A dry run never carries on or puts back an update cut short; it says one is there. It needs an install with its versions side by side (`~/.local/share/bosun-versions`, which `get.sh` makes); in a checkout of your own, update with git. The install line run again hands over to it, and its first run converts a checkout an older `get.sh` made, once: it refuses one with anything of yours in it; once every window is idle and nobody types, it stops bosun's own background work (the watchdog's and learning's jobs, the check-in loop), checks that the moment is still quiet (for two minutes at the most: past that it starts that work again and waits with everything running), swaps the checkout for the link in one step and keeps it as `legacy-<its commit>`, and restarts each of bosun's own windows; stopped short of the switch, or put back, it starts again what it stopped, as it was (after a crash, the install line run again does, as the old checkout has no `bosun update`; see [Updating](setup.md#the-first-update-of-an-older-install)). An update deletes older version folders, but keeps one with a change or a commit of its own in it, as it keeps the checkout from before versions while anything of yours is in it, and its summary says so; one a running process still uses is left to a later update. See [design/update.md](design/update.md) |
| `bosun morning [--dry-run] [--skip-setup] [--awake-minutes N]` | The scheduled entry point: keeps awake, runs the setup steps, updates the agents that bosun starts with their own auto-update off (`agy update`, once, before the windows start or refresh; a failure is a problem in the notification and stops nothing), then starts or refreshes the windows. `--skip-setup` skips the setup steps only. After a `bosun quit` that paused the morning start it logs that and exits 0 before doing anything, until `bosun start`; after one that did not, it starts as usual and ends the quit |
| `bosun setup [--dry-run]` | Run (or just check) the setup steps |
| `bosun alert [--dry-run] <message>` | Notify you: a macOS notification and, with `BOSUN_ALERT_SLACK_USER` set, a Slack DM to yourself sent by a headless Claude that can use only Slack's send-message tool and never waits for an approval |
| `bosun attach` | Attach to the session on its own tmux server (`tmux -L <socket> attach -t <session>`) |
| `bosun start [--restart] [--unless-active]` / `bosun stop [--keep-awake]` | Start the tmux session (or refresh it if it exists), or stop it; stop also releases the keep-awake, unless `--keep-awake` leaves it (the caffeinate and its files) alone. One start or refresh at a time: a second waits for the first, up to 3 minutes. `--restart` refuses inside bosun's own windows, which it would stop; `stop` works there, stopping its own window last. A start also ends a `bosun quit`: the watchdog, learning and the morning job run again |
| `bosun quit --plan [--json]` / `quit (--let-finish[=<minutes>] \| --stop-now) [--pause-morning] [--sleep] [--json]` | Stop bosun until `bosun start`, with your say over what is busy, the morning start and the Mac's keep-awake; it never touches the ledger, the knowledge base or the config. `--plan` changes nothing: it says which windows are open, busy and waiting for you, when the keep-awake ends, and why a quit is refused. `--let-finish` waits until no window is `busy`, checking every 5 seconds for up to `<minutes>` (default `BOSUN_QUIT_WAIT_MINUTES`, 10; 0 checks once): a window waiting at a prompt does not hold the wait (it is listed and stopped with the rest), one at `shell` has only background work and counts as done, and no key is ever sent to a window. If the minutes run out it changes nothing, names the windows still busy and exits 3, so the caller can wait longer or use `--stop-now`; `--stop-now` quits at once. A quit writes `quit.json` first (the watchdog, scheduled learning and a paused morning skip their runs from then on, and never restart what is being stopped), takes away the console job's `console/wanted` marker and stops the job (a console you started by hand is not the job: if one still runs, it says so), then runs `bosun stop --keep-awake`; `--sleep` runs a plain `bosun stop` so the Mac may sleep now, and `--pause-morning` keeps the morning start off until `bosun start` (without it the next morning run starts bosun again). While an update runs it is refused (exit 1); `bosun stop` failing fails it (exit 1), leaving `quit.json`. `--json` prints one object with `contract` 1: the plan, and for a quit its `result` (`stopped`, `busy`, `refused` or `failed`). Run it from outside bosun's windows |
| `bosun refresh [--dry-run] [--drain-only] [--restart-idle] [--unless-active] [window...]` / `refresh [--dry-run] --update-restart <prompt-file> <window>` / `refresh [--dry-run] --checkin-loop` | Per window: restart idle sessions on an outdated agent or with a changed model or effort, send the drain prompt to idle ones with work in flight, relaunch exited ones (see [Steady state](setup.md#steady-state-the-session-already-exists)). For an update: `--update-restart` restarts one window now if its turn is over (idle, or `shell`: only background work runs) and nobody is typing there (`send`'s check), resuming its conversation with the prompt in the file instead of the drain prompt. A busy or waiting window, or one whose input box holds unsent text, is left running and refresh exits 3, so the caller can try again. An orchestrator still on yesterday's conversation starts today's with the morning chores instead, as on a new day, and a repo window with a fresh conversation pending starts that one; a window whose agent is not running is relaunched (a missing one created) with the update's prompt only when its launch resumes a conversation, and otherwise starts as a new conversation does. A window started into its next conversation gets that one's own prompt, not the update's, so refresh exits 4; every window starts on the agent its last launch ran, even if `harness:` or `BOSUN_HARNESS` now names another (that one takes over at the next `refresh` or `start` not for an update), and a window outside the window list (opened by `send --new`) keeps the directory and `--model` / `--effort` its launch recorded; one with no launch recorded is refused, as bosun did not start it. `--checkin-loop` restarts the check-in loop in the `checkin` window, which otherwise keeps the code it started with; it stops the loop at once, even in the middle of a tick, so call it while an update holds bosun's background work. Neither takes another mode, `--unless-active` included |
| `bosun launch [--model M] [--effort E] [--harness H] [--no-prompt] <name> [prompt \| --prompt-file <file>]` / `launch --fingerprint <name>` | Resume a named session in the current directory, with the window's model and effort (`--harness`: on that agent instead of the configured one), and record what the agent was launched with (`launches/<session>/<name>.json` in the state folder: bosun's commit, the agent and the model and effort it runs with, the directory, a `--model` / `--effort` it was given, and a fingerprint of the agent's arguments and the files they name in the install, with the conversation's name and the orchestrator's policy text left out). `--fingerprint` prints the fingerprint a launch would record now, as an update would start the window again (on the agent it was launched on), and launches nothing: in the window's directory from the window list, or for a window outside it (opened by `send --new`) with the directory and `--model` / `--effort` its last launch recorded; it refuses a window with neither |
| `bosun send --list` / `send <window> <msg>` / `send --new [--model M] [--effort E] <window> <dir> <msg>` / `send --start <window> [msg]` | List windows with their agent, status and version (`claude:idle`, `codex:busy`, `no-agent`); hand work to a running session (bracketed paste, so multi-line text arrives as one prompt; refused while Claude waits at a permission prompt or question; it waits while someone typed in that window within `BOSUN_SEND_TYPING_MINUTES` or its input line holds unsent text, up to `BOSUN_SEND_WAIT_SECONDS`, and fails unless Claude took the prompt, so the caller resends), open a new window, or start Claude in a window that has none (resuming its named session; without a message it gets the drain prompt). A message of `-` is read from stdin. `--id <ledger id>` names the work item (checked, prefixed, noted in its history); the orchestrator must give `--id` or `--no-item`. `--new` and `--start` run `bosun launch` as the pane's own command, with the task in a prompt file, and exit 0 only once Claude is running. |
| `bosun delegate <type>[,<type>] --id <ledger id> --ask "<one line>" [--details ...] [--model M] [--effort E] (--print\|--window W\|--new W DIR\|--start W) [--again]` / `--update <ledger id> --details ... [--window W]` / `--list` | Hand a task to a repo session, with the rules for its task type from `orchestrator/tasks/`, and record the window on each item; refused while the item's last hand-over awaits a report, unless `--again`. `--update` sends an addendum to that window, framed with the item's id and kept in its history; with `--window` it moves the item: the new window gets the whole task, the old one is told to stop. `--update <out-id>` hands an outreach reply to the window holding its parent and marks it applied |
| `bosun chores [morning\|check-in] [--dry-run [--fresh\|--continue]]` | Tell the orchestrator to run its chores now, or rehearse them headless with no side effects |
| `bosun checkin [--loop] [--dry-run]` | Send `/bosun:chores check-in` if the orchestrator is idle and you are not typing (the `checkin` window loops this) |
| `bosun ledger <command>` | Work-item ledger: `list`, `show`, `upsert`, `transition`, `note`, `report` and `reports` (repo sessions' outcomes, with `--ci` the CI status of a pushed PR; `--since` lists every one, with what I said in the window), `delegation` (where an item was handed over, and whether its window is working on it), `said` (what I typed in repo windows), `working` and `idle` (which item a window works on), `in-flight` (whether a window holds work), `compact-context` (what a window gets back after compaction), `record-delegation`, `record-update` and `record-move` (used by `bosun delegate`), `propose` (with `--send`, `--run` or `--tool`: the exact outward call), `approve` and `approvals` (see [Approvals](permissions.md#approvals-approve-once-in-chat)), `resolve`, `resolve-carried-out` (one-time: settle proposals whose approved call ran before the PostToolUse hook, by the transcript), `seen`, `record-source`, `kinds` (id formats, Slack classes, state machines), `mark-run` (also prints where the Slack scan starts), `prune`, `render`, `diff`; outreach (see [Waiting on someone](orchestrator.md#waiting-on-someone-outreach)): `reach-out` (alias `ask`), `sent`, `replied`, `outreach`; tasks and links (see [Tasks and links](orchestrator.md#work-we-take-on-tasks-and-links)): `spawn`, `link`, `unlink`, `fold`, `tree`, `migrate-links`; tickets (see [External tickets](orchestrator.md#external-tickets)): `ticket-sync`, `tickets`; workstreams (see [Workstreams](orchestrator.md#workstreams-what-an-item-is-for)): `ws add|list|show|set-state|alias`, `assign`, `summary`, `lint`, `list --ws`; checks: `validate [--journal]` |
| `bosun guard [--approvals\|--permission-request\|--post-tool-use]` | PreToolUse hook for the orchestrator (see Permissions); with `BOSUN_APPROVALS_ENABLED=1` also its approval hooks (see [Approvals](permissions.md#approvals-approve-once-in-chat)) |
| `bosun hook user-prompt\|compact-context\|signal\|turn-end\|agent` | What the agents call: Claude Code's hooks, what an agent that reports its turns (Codex) runs when one ends, as `turn-end --harness <agent>` (Codex windows started before that keep `codex-turn-end`, which works as before), and `agent --harness <agent> --event <event>`, an agent's own hooks (the plugin bosun installs into Antigravity runs it): the hook's JSON in on stdin, the agent's answer out on stdout, in the foreground whether or not events are on, and always exit 0, since the agent takes any other exit as a refusal of its tool; an error is a line in the hook log. Among them, what records what I type in a window (see [Events](events.md#events-from-repo-sessions)) |
